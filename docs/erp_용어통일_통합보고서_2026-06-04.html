🎯 결론

ERP와 챗봇이 모두 내부 개발팀으로 이관 예정이므로, 외주 협의·비용·외부 API 의존이 0으로 떨어집니다.
현재 회의 도구의 Firestore = 전사 SSOT(Single Source of Truth)로 두고 ERP·챗봇·상품DB가 이를 참조·동기화하는 구조로 가면 "한 곳 수정 = 다 적용"이 실제로 실현됩니다. 총 작업 기간 3~6주, 외주비 0원으로 추진 가능합니다.

1. 배경 및 현황

1.1 문제 정의

현재 자재·공정·장비 명칭이 시스템마다 다르게 표기되어 운영 효율과 매출에 영향을 주고 있습니다.

2. 통합 아키텍처

2.1 핵심 원칙: SSOT (단일 진실 소스)

전사 시스템 중 한 곳만이 자재·공정·장비 명칭의 "정답"을 가져야 합니다. 이 도구가 그 역할을 맡습니다.

┌─────────────────────────────────────────┐ │ 통일 용어 도구 (Firestore + 협업 페이지) │ ← 한 곳에서 수정 │ · confirmed 상태 = 5명 동의 후 │ │ · 변경 이력 영구 보존 │ │ · UNDO / CSV 추출 가능 │ └─────────────────┬───────────────────────────┘ │ 변경 감지 (Cloud Function) ▼ ┌─────────────────────────────────────────┐ │ 통합 sync 레이어 (개발팀 관리) │ └────┬──────────┬──────────┬────────────────┘ ▼ ▼ ▼ ┌────────┐ ┌─────────┐ ┌──────────┐ │ ERP │ │ 상품DB │ │ 챗봇 │ │(내부) │ │(시트) │ │(내부) │ └────────┘ └─────────┘ └──────────┘

2.2 통합 방식 — 3가지 옵션

A. 직접 참조 방식

ERP·챗봇이 자체 DB 없이 통일 용어 도구의 Firestore를 직접 read

장점
• 변경 즉시 반영 (sync 지연 0)
• 데이터 일관성 100% 보장
• 추가 인프라 불필요
단점
• ERP·챗봇 코드 변경 큼
• Firestore 장애 시 전사 영향
• 기존 마스터 마이그레이션 필요

B. Webhook 기반 sync

ERP·챗봇은 자체 DB 유지, confirmed 변경 시 Cloud Function이 푸시

장점
• ERP·챗봇 코드 변경 최소 (API 1~2개씩)
• 위험도 낮음, 단계적 도입 가능
• Firestore 장애와 분리됨
• 롤백 쉬움
단점
• 수 초~분 단위 sync 지연
• 통합 sync 레이어 1개 운영 필요

C. 양방향 매핑 테이블 (오버레이)

ERP·챗봇 표시명 변경 안 함, 화면 표시 직전 통일명으로 매핑

장점
• ERP DB 안 건드림 → 가장 안전
• 과거 데이터 영향 0
단점
• 모든 표시 경로마다 매핑 호출
• 시스템 분산도 높음
• 코드 손대는 곳이 더 많음
권장: B (Webhook sync)
개발팀 작업량이 가장 적고 위험도가 낮습니다. 향후 A로 전환할 때도 자연스럽게 마이그레이션 가능합니다. C는 ERP가 레거시이고 마이그레이션 불가할 때만 선택합니다.

5. 통합 설계 원칙 (반드시 지킬 것)

원칙이유 및 적용 방법
ERP 코드(ID) rename 절대 금지 기존 주문·매출·재고·이력의 모든 매칭이 깨짐. 표시명만 변경하고 ID는 영구 유지. 매핑 테이블에 erp_id → unified_name 양방향 보관.
양방향 매핑 테이블 보존 옛 이름 ↔ 새 이름 ↔ ERP 코드 ↔ 고객 표현 4-way 매핑. 옛 자료 검색·이력 추적·고객 문의 응대에 필수.
동의어 사전 방식 (챗봇) 통일 명으로 바꿔도 고객은 옛 이름·습관 표현으로 검색·문의. 챗봇은 모든 동의어를 같은 노드에 매핑하여 응답 일관성 확보.
confirmed 후에만 시스템 푸시 협의 중인 임시값이 ERP나 챗봇에 들어가면 사고. 5명 동의(전체동의 체크) 완료 항목만 sync 큐에 들어감. 이미 도구에 가드 적용됨.
변경 이력 영구 보존 "왜 이 이름으로 바꿨는지", "누가 언제 결정했는지" 분기·연 단위 추적 가능해야 함. erp_term_logs 컬렉션이 이 역할 수행 중.
UNDO 가능성 유지 잘못된 sync는 역으로 되돌릴 수 있어야 함. Webhook은 양방향(set/unset) 지원 필요. 현재 도구의 UNDO 20회와 연계.

6. 주요 리스크 및 대응

리스크발생 가능성영향도대응 방안
ERP 코드 실수로 rename → 이력 깨짐 중간 치명적 도구 차원에서 erp_id 컬럼 readonly 처리, 개발팀 API에서도 ID 변경 거부
sync 지연·실패로 ERP-챗봇 불일치 중간 중간 Cloud Function 재시도(최대 3회), 실패 시 로그·알림. 매일 1회 정합성 확인 배치
회의 중 잘못된 결정 → 시스템에 반영 낮음 중간 5명 confirm 가드 + UNDO 20회. 추가로 confirmed 후 24시간 지연 sync 옵션 가능
외부에서 Firestore 무단 조작 중간 치명적 Firebase 콘솔에서 보안규칙 게시 필요 (현재 무인증 공개 상태 — 미팅 후 즉시 작업 권장)
개발팀 일정 지연 중간 중간 Phase 0(수동)으로 그대로 운영 가능. Phase 1(시트)부터 외주 0으로 자체 진행

7. 회의 도구 보강 권장 (15분 작업)

Phase 2~3 작업을 부드럽게 받기 위해 현재 회의 도구에 두 컬럼만 더 추가하면 좋습니다.

추가 컬럼역할예시
erp_id ERP 내부 코드(절대 변경 금지 대상). Phase 2에서 ERP API 호출 시 필수 키. 1 (포맥스3T) · 104 (스텐304)
synonyms 옛 이름·고객 표현·약어 모음. 챗봇 동의어 사전에 그대로 import. "포맥스ǀ포맥스 3TǀPVC 폼보드ǀ폼보드ǀ포멕스"
회의 중에 이 두 컬럼을 같이 채워두시면 회의 시간은 30분 정도 늘어나지만, Phase 2~3 본격 시작 시 며칠 분량의 데이터 정리를 절약합니다.

8. 다음 액션 (의사결정 사항)

8.1 즉시 결정 (이번 미팅 또는 다음 영업일)

  • 회의 도구에 erp_id, synonyms 컬럼 추가 진행 여부 (15분 작업)

  • 개발팀과 통합 설계 협의 미팅 잡기 (Phase 2 ERP·챗봇)

  • 챗봇 외주사 인수인계 일정 확인 (개발팀 이관 시점)
